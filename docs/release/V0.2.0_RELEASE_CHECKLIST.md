### Prior evidence (credit)

- `docs/validation/V0.2.0_PILOT_CHECKLIST.md` M4-04-04 / M4-04-05: production-signed pilot APK (`0.2.0-pilot.1`, versionCode 2, commit `6dc1bc1`, signer certificate SHA-256 `92a578e8…` = **same production certificate as published v0.1.0**) installed over the published v0.1.0 APK on Moto Edge 60 Fusion (serial `ZA22374XPC`, API 36). - `FarmBackupIntegrationTest#postUpgradeNewTransactionAppearsInBackupExport` (instrumentation, on-device) — post-upgrade transactions appear in fresh exports.
- The v0.1.0 published release is real and immutable: tag `v0.1.0`, published 2026-08-05, release asset `app-release.apk` SHA-256 `990c1009…7bd7bc` verified against `RELEASE_NOTES_0.1.0.md:55` and the downloaded `.sha256`.

### Residual gap

The migration path from published v0.1.0 → current `main` was exercised on the **pilot candidate** (`0.2.0-pilot.1`, versionCode 2, commit `6dc1bc1`), **not** on the current v0.2.0 candidate (versionCode 3, `main` at `3dba875`). RC-01 must re-run the upgrade gate on the **actual** candidate that will be tagged `v0.2.0`.

> This gate is deliberately not executed during RC-00 (audit only). It becomes executable once the release candidate is fixed (RC-01).

### Defined RC-01 procedure (to execute, not yet run)

1. Build the production-signed candidate APK for the exact commit to be tagged `v0.2.0` (via the policy's `Release launcher`, or a same-signer debug-equivalent build for volume testing — RC-01 records which). Signer certificate must equal `92a578e8…` (v0.1.0 continuity).
2. On the physical device (Moto Edge 60 Fusion, API 36), clean-install the **published `v0.1.0` APK** from the GitHub release and create representative v0.1.0-era data: farm + several income/expense transactions with known minor-unit totals + at least one entry.
3. `adb install -r` the v0.2.0 candidate over v0.1.0 (same-signer upgrade).
4. Verify: farm opens; all pre-upgrade transactions/entries persist; totals and balance identical to pre-upgrade; migration to schema v6 occurred deterministically (`FarmSliceServiceTest` migration suite re-run on the candidate head).
5. Exercise new v0.2.0 functionality after upgrade: Party CRUD, a SALE + settlement, a PURCHASE + settlement, Party Khata opening, Financial Overview period switch, Party Hisab, and one M6.3/M6.4 calculator — no crash, no data loss.
6. Force-stop and cold relaunch; then full device reboot and relaunch; re-verify the same invariants.
7. Export a fresh backup; decode and verify it contains the full post-upgrade state; then restore into a cleared store and verify invariants (or use the existing on-device backup tests plus a manual export).
8. Record exact APK SHA-256, commit hash, and every observation in this checklist's Section C log.

**Gate: `NOT RUN` for the current candidate** (prior pilot evidence: `PARTIAL` precedent, not a substitute).
